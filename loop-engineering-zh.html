循环工程
Loop Engineering

把「给智能体写提示的人」这个角色，从你身上拿掉——改为由你设计那套替你写提示的系统。

作者：Addy Osmani　·　首发：2026 年 6 月 7 日　·　原文：addyosmani.com/blog/loop-engineering

循环工程，就是把你从「给智能体写提示的人」这个位置上替换掉。你改为设计那套替你完成这件事的系统。

这里的「循环」可以理解为一种递归目标：你定义意图，AI 反复迭代直到完成。我相信这可能就是我们与编码智能体协作的未来。不过现在还早，我持怀疑态度；而且你必须对 token 成本非常小心（token 宽裕的人和 token 拮据的人，使用模式可能天差地别），所以我想把它是什么、意味着什么，拆开讲清楚。

＊文中对 Claude Code 的引用来自 Boris Cherny（Anthropic 的 Claude Code 负责人）。

理解图 ①　一个循环的五步闭环 + 一个状态脊梁。五个部件（自动化、工作树、技能、连接器、子智能体）都只是这条闭环上的一个位置；「你」只在最上方出现一次。

Peter Steinberger 最近说过：「你不应该再给编码智能体写提示了。你应该设计那些会去提示你的智能体的循环。」

类似地，Anthropic 旗下 Claude Code 负责人 Boris Cherny 说：「我已经不再提示 Claude 了。我有一堆循环在跑，是它们提示 Claude、并判断该做什么。我的工作是写循环。」

好，那这些话到底是什么意思？

大概过去两年，你从编码智能体那里拿到结果的方式，就是写一个好的提示、给足上下文。你输入一段，看它返回什么，再输入下一段。智能体是一件工具，而你从头到尾握着它，一轮接一轮。那个阶段某种程度上已经结束了——至少有人认为它将要结束。

现在你改为搭建一个小系统：它自己去找活儿、派活儿、检查活儿、把做完的事记下来，然后决定下一件事；你让这个系统去戳那些智能体，而不是你自己去戳。我之前写过它的近亲——智能体外壳工程（agent harness engineering），也就是去搭建单个智能体运行所处的那个环境；还有工厂模型（the factory model）——搭建生产软件的那套系统。循环工程比「外壳」高一层：它仍然是外壳，但它跑在定时器上，它会衍生出一些小帮手，而且它能自给自足（自己喂自己）。

真正让我意外的是：这已经不太是「工具」层面的事了。一年前你想要一个循环，得写一大堆 bash，然后永远维护那一堆东西，它是你的、也只属于你。现在这些组件直接随产品发布。Steinberger 列的那份清单，几乎能一一对应到 Codex 应用上，然后又能几乎同样地对应到 Claude Code 上。而一旦你发现两者的形状是同一个形状，你就不会再争论用哪个工具了——你只需设计一个无论你碰巧坐在哪个工具里都依然能跑的循环。

五个部件，以及一些说明

一个循环需要五样东西，外加一个用来记事的地方。我先把它们列出来，再做映射。

  1. 自动化（Automations）：按计划触发，自己完成发现与分诊（discovery and triage）。
  2. 工作树（Worktrees）：让两个并行工作的智能体不会互相踩脚。
  3. 技能（Skills）：把项目知识写下来，免得智能体只能靠猜。
  4. 插件与连接器（Plugins and connectors）：把智能体插进你已经在用的工具里。
  5. 子智能体（Sub-agents）：让其中一个负责出主意，另一个负责检查。

然后是第六样东西——记忆（memory）。一个 Markdown 文件，或一块 Linear 看板，任何活在「单次对话之外」、记录着「什么是已完成、什么是下一步」的东西。听起来蠢得不值一提。但这是所有长时间运行的智能体都依赖的同一个技巧，我在《长时间运行的智能体》里展开过：模型在两次运行之间会忘掉一切，所以记忆必须落在磁盘上，而不是放在上下文里。智能体会忘，但仓库不会忘。

现在两个产品都已经具备这全部五样东西了。

名字在这儿那儿会有点不同，但能力是同一件事。我逐条讲一下，因为老实说，细节才是决定一个循环能立得住、还是会到处悄悄漏气的地方。

自动化，这是心跳

自动化是让一个循环真正成为「循环」、而不只是你跑过一次的单次运行的东西。在 Codex 应用里，你在 Automations 标签页创建一个，选项目、选它将运行的提示、选频率，以及它是跑在你的本地检出上还是跑在一个后台工作树上。那些发现了东西的运行会进入 Triage 收件箱，而那些什么都没发现的运行会自己归档——这挺不错。OpenAI 内部就用它处理一些无聊事，比如每日 issue 分诊、汇总 CI 失败、撰写提交简报、追捕上周某人引入的 bug。而且一个自动化可以调用一个技能，这样你就能让这件反复发生的事保持可维护：你触发 $skill-name，而不用把一大堵指令墙粘贴进一个永远不会有人更新它的计划任务里。

Claude Code 用调度和 hooks 到达同一个地方。你可以用 /loop 按间隔运行一个提示或命令，可以安排一个 cron 任务，可以用 hooks 在智能体生命周期的某些节点触发 shell 命令，或者干脆把整件事推到 GitHub Actions 上，这样你合上笔记本之后它还在继续跑。完全相同的思路：你定义一个自主任务，给它一个节奏，然后发现结果会自己送到你面前，这样你就不必成为那个四处巡检查看的人。

还有第二个「会话内」的原语值得知道，它更贴近这篇帖子真正在讲的东西。/loop 按节奏重跑。/goal 则一直跑到你写的某个条件真正为真为止；而且每一轮之后，都会有一个独立的小模型来检查你是否完成了——所以写代码的那个智能体，并不是给它打分的那一个。你给它类似「test/auth 下的所有测试通过、且 lint 干净」这样的条件，然后就走人。Codex 也有同样的东西，也叫 /goal，它会跨多轮持续工作，直到某个可验证的停止条件成立，带有暂停、恢复和清除的功能。同一个原语，两个工具都有——这大概就是贯穿全文的那种模式。

所以这部分是「把活儿浮出来」的部分。循环的其余部分，才是对活儿动手的部分。

工作树，让并行不变成混乱

你一旦跑不止一个智能体，文件就开始互相碰撞，而这会成为故障点。两个智能体写同一个文件，和两名工程师各自提交到同样的代码行、之前又没沟通一样让人头疼。一个 git 工作树能解决它：它是共享同一份仓库历史、但拥有自己分支的独立工作目录，所以一个智能体的编辑在物理上就碰不到另一个的检出。

Codex 把工作树支持直接内置了进来，于是多个线程能同时打同一个仓库而不会互相撞车。Claude Code 用 git worktree、一个用来在自己检出里开一个会话的 --worktree 标志，以及一个你可以挂在子智能体上的 isolation: worktree 设置，给你同样的隔离——每个帮手都拿到一份用完之后会自我清理的干净检出。我在《编排税》里写过这一切「人」的那一面：工作树移除了机械上的碰撞，但你自己仍然是天花板——决定你到底能同时跑多少个的，是你的评审带宽，而不是工具。

技能，让你不必每次重讲一遍你的项目

技能是让你不再像金鱼一样、每个会话都要重新解释同一份项目上下文的方式。两个工具使用同一格式：一个文件夹，里面放一个 SKILL.md，承载指令和元数据，再加上可选的脚本、参考资料、资源文件。当你用 $ 或 /skills 调用时，Codex 会运行一个技能；或者当你的任务匹配到该技能的描述时，它会自动运行——这正是「一句朴素紧实的描述胜过一句花哨描述」的原因。Claude Code 的做法也一样，我在《智能体技能》里写过这个模式。

技能也是「意图」不再反复让你付出代价的地方。我在《意图债》里论证过：智能体每次会话都从冷启动开始，它会用自信的猜测去填补你意图里的任何空洞。技能就是把那份意图写在外部——约定、构建步骤、「我们不这么干，因为出过那样一次事故」——一次写好，让智能体每次运行都读到它。没有技能，循环每个周期都要从零重新推导你的整个项目；有了技能，它就会（大致上）累积复利。

有一件事要拎清：技能是创作的格式，而插件是把它发布出去的方式。当你想跨仓库共享一个技能、或把几个技能打包到一起时，你把它们打包成一个插件。在 Codex 成立，在 Claude Code 也成立。

插件与连接器，让循环触达你真实的工具

一个只能看到文件系统的循环，是个很小的循环。连接器（构建在 MCP 之上）让智能体能读你的 issue 跟踪器、查询数据库、访问预发环境的 API、往 Slack 里丢条消息。Codex 和 Claude Code 都会说 MCP，所以你为其中一个写的连接器，通常换到另一个也能直接用。而插件把连接器和技能打包在一起，于是你的同事可以一次性安装好你的整套配置，而不用靠记忆把整个东西重新搭一遍。

这就是「一个说『这是修复方案』的智能体」和「一个自己去开 PR、关联 Linear 工单、并在 CI 变绿后 ping 一下频道」的循环之间的区别。连接器，就是循环能在你真实环境里动手、而不只是告诉你「如果它能动手它会怎么做」的原因。

子智能体，让「出主意的人」远离「检查的人」

在一个循环里，最有用的一项结构性安排，迄今为止，就是把「写的人」和「检查的人」拆开。写代码的那个模型，给自己批改作业时实在太宽容了。第二个智能体，带着不同的指令、有时甚至是不同的模型，能抓住第一个智能体把自己说服进去的那些问题。

Codex 只在你要求时才衍生子智能体，让它们同时运行，然后把结果折叠回一个答案里。你把自己的智能体定义为 .codex/agents/ 里的 TOML 文件，每一个有名字、描述、指令，以及可选的模型和推理强度——所以你的安全审查员可以是一个高推理强度的强模型，而你的探索者可以是某个快速的只读小东西。Claude Code 用 .claude/agents/ 里的子智能体和在它们之间传递工作的智能体团队做同样的事。两者常见的分工都是：一个智能体探索、一个实现、一个对着规格做验证。

这个论点我已经说过两次了，一次是在《代码智能体乐团》里，一次是在《AI 时代的智能体代码评审》里。它之所以特别地在循环里重要，是因为循环是在你不看着的时候跑的——所以一个你真正信任的验证者，才是你能走开的唯一理由。子智能体确实更烧 token，因为每个都要做自己的模型和工具调用，所以要把它花在「第二意见值得付钱」的地方。这基本上也是 Claude Code 的 /goal 在底层做的事：由一个全新的模型来判断循环是否完成，而不是由那个干了活的模型来判断——「制造者与检查者分离」被应用到了停止条件本身。

一个循环长什么样

把它们拼起来，一条单独的线程就变成了一块小小的控制面板。下面是我一直在用的一种形状。

一个自动化每天早上在仓库上运行。它的提示调用一个分诊技能，该技能读取昨天的 CI 失败、未关闭的 issue、最近的提交，然后把发现写进一个 Markdown 文件或一块 Linear 看板。对每一个值得动手的发现，这条线程会开一个隔离的工作树，派一个子智能体去起草修复，再由第二个子智能体对照项目技能和现有测试来评审那份草稿。

连接器让循环能开 PR、更新工单。循环处理不了的任何东西，都会落到我面前的 Triage 收件箱里。状态文件是整件事的脊梁：它记住什么被尝试过、什么通过了、什么还开着，于是第二天早上这次运行会从今天停下的地方接着往下走。

看看你刚才实际上做了什么。你一次性把它设计出来。你没有去提示其中任何一个步骤。这就是 Steinberger 那个观点被做成了现实；而它在 Codex 里、在 Claude Code 里是同一个循环，因为这些部件就是同一批部件。

循环仍然做不到的事

循环改变了工作，它并没有把你从中删掉。而且有三个问题，会随着循环变得更好而实际上变得更尖锐，而不是更容易。

验证仍然落在你身上。一个无人值守地运行的循环，也是一个无人值守地犯错的循环。你把验证者子智能体从制造者那里拆出来的全部理由，就是让循环的「它完成了」这句话有点分量——但即便如此，「完成」是一个主张，而不是一份证明。我在《AI 时代的代码评审》里一直重复同一句话：你的工作是交付你已确认能正常工作的代码。

你的理解仍然会腐烂，如果你放任它的话。循环交付的、不由你写的代码越快，在「存在的东西」和「你真正理解的东西」之间的缺口就越大。这就是理解债（comprehension debt），而一个顺滑的循环只会让它增长得更快——除非你去读循环做出来的东西。

而那副舒服的姿态，才是最危险的姿态。当循环自己运行起来的时候，非常容易就不再持有自己的观点，只是接受它返回的任何东西。我把它叫做认知投降（cognitive surrender）。带着判断力去设计循环，它是解药；为了逃避思考去设计循环，它是加速剂——同一个动作，相反的结果。

理解债 · comprehension debt

代码库里存在的东西，与你真正理解的东西之间的差距。循环越顺滑，这个差距扩得越快——除非你亲自读它产出的东西。

认知投降 · cognitive surrender

因为循环能自己跑，就放弃持有自己的判断、照单全收它的结果。设计循环既可以是解药，也可以是加速剂，取决于你是否带着判断力。

意图债 · intent debt

智能体每次会话都冷启动，会用自信的猜测填补你意图里的空洞。技能就是把意图写在外部，一次写好、每次读到。

编排税 · the orchestration tax

工作树消除了机械层面的碰撞，但能同时跑多少个循环，上限是你的评审带宽——天花板是你，不是工具。

搭建循环，保持做工程师

我认为这是我们工作方式将如何演进的一次预演。话虽如此，如果我不亲自评审代码，或者如果我完全依赖自动化循环去修它，我产品的质量会受损。我大概率会陷进一个向下的螺旋，不断把自己往更深的坑里挖。

话虽如此，去搭你的循环吧，但别忘了，直接提示你的智能体也仍然有效。关键在于找到正确的平衡。

循环的结果也取决于你，会因人而异。两个人可以搭出一模一样的循环，却得到完全相反的结果。一个人用它在自己理解得很深的工作上跑得更快；另一个人用它来彻底逃避理解这份工作。循环分不出区别。你能。

这正是为什么循环设计比提示工程更难，而不是更容易。Cherny 的观点不是说活儿变简单了，而是说杠杆点移动了。

搭建循环。但要像一个打算继续做工程师的人那样去搭它，而不只是那个按下「开始」的人。
